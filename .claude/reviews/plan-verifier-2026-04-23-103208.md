### [断言 4] Step 6(a) note on `OutputFormatting` omitting null-valued fields is potentially misleading

Plan line 416 says: *"Round-trip of absent → nil → encoded-as-null is acceptable (`JSONEncoder.OutputFormatting` may omit null-valued fields depending on config, but `decodeIfPresent` on the receive side handles both shapes)."*

**Verification:** `JSONEncoder.OutputFormatting` is an `OptionSet` with `.prettyPrinted`, `.sortedKeys`, `.withoutEscapingSlashes`. None of these options omit null-valued fields. `JSONEncoder` by default **emits `null` for nil values** when the key is encoded (via `encode(_:forKey:)`) and omits only when `encodeIfPresent` is used.

The current `persist(...)` in `RouterConfigurationStore.swift:177` uses `encoder.outputFormatting = [.prettyPrinted, .sortedKeys]`, and the synthesized Codable encode for `StoredConfiguration` uses `encode(...)` on non-`let ... = nil` fields, `encodeIfPresent(...)` on defaulted ones.

With the `let ... = nil` approach in Step 6(a), the compiler warning already told us decode skips these keys entirely. For encode, the synthesized `encode(to:)` **also omits** immutable-defaulted properties from the output JSON. So on-disk, `config.json` would never contain `pendingToolTurnTTLSeconds` or `advisorContextMessageLimit` at all.

**Result:** ❌ 断言成立 [C:80] (secondary issue, subsumed by 断言 1)

**Consequence:** Even the "encoded-as-null" fallback described in the note doesn't happen. The encoded JSON simply lacks these keys. Combined with 断言 1 (decode ignores them regardless), they become dead storage — user Settings changes never persist, never load.

**计划需补充:** If Step 6(a) is revised per 断言 1 Option A (remove inline `= nil`), then encode and decode both participate correctly and this note becomes moot. If Option B (explicit CodingKeys + custom `init(from:)`), the note should be updated to reflect that the custom init governs decode while encode still works via synthesized path with explicit `encodeIfPresent`.
