### Spacing Rhythm

#### Upstream tab section ordering (SettingsView.swift)

```
Route (visualization card)         ← MBCard within MBSection
Upstream                            ← TextField only
Routing rules                       ← List + Add button
Fallback route                      ← RouteDraftPickers
Advisor route                       ← RouteDraftPickers
Subscription auth                   ← path field + auth dot + conditional next-step
Token status                        ← token value + last refresh + state dot + refresh button
[Save / Reload buttons]
```

**Spacing between MBSections:** Every section uses `MBSection` which enforces `.padding(.bottom, 18)`. All sections are therefore at uniform 18pt separation. This is consistent with the General tab sections above it. PASS.

**Internal spacing of new sections:**
- `RoutingRuleDraftRow` (line 633): `.padding(.vertical, 6)` — compact for list rows, appropriate.
- `RouteDraftPickers` (line 641): `HStack(spacing: 8)` — matches the horizontal layout of the parent `MBField` rows which do not add extra vertical padding.
- `Token status` section: Uses `MBField` throughout, which adds `.padding(.vertical, 10)` per row internally. Consistent with every other `MBField` usage on this tab and the General/Gateway tabs. PASS.

**Add button placement:** `Add rule` button (line 423) sits directly below the `List` card with no extra spacing modifier — it attaches to the card bottom at the default 8pt MBSection gap. Reasonable, but see Note 1 below.

**Overall:** Spacing is uniform and consistent. No patchwork feel.

### Consistency with Existing Sections on the Same Tab

#### Token status section vs. Subscription auth section
Both appear on the same Upstream tab. Both use `MBField` with `MBColor.inkMid` for value text. Both include a status dot. Both include conditional content below the main fields. PASS.

#### Routing rules vs. Diagnostics tab list patterns
The Diagnostics tab uses `MBTerminalPanel` for log lines, and the General tab uses `MBReadOnlyField` cards. The Routing rules list uses a plain `List` wrapped in `MBCard(padding: 0)`. This is a slight divergence — other lists on the tab are not wrapped in MBCard. However, the Routing rules list is the only editable list on the tab, and wrapping it in a card provides the right visual affordance (it looks like a table editor). **Not a must-fix, but worth noting as a pattern variance.** Marking as advisory.

#### Save/Reload button row (lines 520-529)
The `GatewaySettingsTab` (line 283-290) uses:
```swift
HStack {
    Spacer(minLength: 0)
    Button(action: { model.saveGatewaySettings() }) {
        Label("Save gateway", systemImage: "tray.and.arrow.down")
    }
    .buttonStyle(.borderedProminent)
}
.padding(.top, 4)
```

The `UpstreamSettingsTab` uses:
```swift
HStack(spacing: 8) {
    Button(action: { model.reloadPersistedConfiguration() }) { ... }
    Spacer(minLength: 0)
    Button(action: { Task { await model.saveRoutingAndApply() } }) {
        Label("Save routing + upstream", systemImage: "tray.and.arrow.down")
    }
    .buttonStyle(.borderedProminent)
}
.padding(.top, 4)
```

The Upstream tab has two buttons while the Gateway tab has one. The button label ("Save routing + upstream") is significantly longer than "Save gateway" and appears on the right. The Reload button is on the left, visually balanced. Consistent in `.padding(.top, 4)`. **Pass — both tabs follow the same button placement pattern.**

#### routingInsightsSection vs. recentSection on ContentView
Both use `MBSectionHeader` for section labels and both wrap their content in `MBCard(padding: 10, background: MBColor.paperDim)`. The `routingInsightsSection` uses `MBColor.paperDim` for the card background, matching `kpiSection` which also uses `MBColor.paperDim`. The `recentSection` uses a plain `MBCard(padding: 0)` (default `MBColor.paperAlt` background). This is intentional differentiation (KPI and routing insights are read-only display cards; recent activity is a list). PASS.

### Color Usage

#### MBDot states
- `routingInsightsSection`: No MBDot used — purely informational. No color risk.
- `Routing rules` section: No MBDot used. PASS.
- `Token status` section (line 495): `MBDot(state: tokenDotState, size: 8)` where `tokenDotState` is a computed property returning `.live / .warn / .fault`. These are the three standard semantic states. No ad-hoc color introduced. PASS.

#### Error text
- `routingSaveError` (line 404-406): `.foregroundStyle(MBColor.faultInk)` — correct semantic use.
- `tokenRefreshError` (line 514-516): `.foregroundStyle(MBColor.faultInk)` — correct semantic use.

Both use `MBColor.faultInk` which adapts via `dynamic(light:, dark:)`. No hardcoded red. PASS.

#### Route visualization (routeVisualization)
- Source label: `MBColor.inkDim` (correct, de-emphasized)
- "Routed to" arrow text: `MBColor.inkFaint` (correct, de-emphasized)
- Upstream name: `MBColor.liveInk` (emphasized via semantic live color)
- Background: `MBColor.liveSoft` with `MBColor.live.opacity(0.3)` border — the live soft/border combo is consistent with `MBPill` live tone pattern. The opacity value of 0.3 is well above the 0.15 risk threshold for dark mode visibility. PASS.

#### Token status section header dot vs. auth dot
Two different MBDot usages on the same section (lines 459 and 495) both use `size: 8`. Consistent. PASS.

### Polish

#### RoutingRuleDraftRow delete button
Line 611-616: Delete uses `Image(systemName: "trash")` with `foregroundStyle(MBColor.faultInk)`. This is the standard destructive action color in the design system. Consistent with how fault color is used elsewhere. PASS.

#### Add rule button
Line 423-425: `Label("Add rule", systemImage: "plus")` uses default button styling (not `.borderedProminent`). On the Gateway tab, standalone action buttons (Reveal, Reload, etc.) use the same plain style. Consistent. PASS.

#### Refresh button in Token status
Line 502-511: `Button(action: { Task { await model.refreshTokenNow() } })` with `Label("Refresh now", systemImage: "arrow.clockwise")`. No `.buttonStyle(.borderedProminent)` applied. This is consistent with the Add rule button and other secondary action buttons. The `.disabled(model.isRefreshingToken)` and `ProgressView()` during loading are correct async UX patterns. PASS.

#### Routing insights metrics alignment
Line 1185-1203: The metrics text is right-aligned within the row via the outer `HStack(spacing: 10)` with `.frame(maxWidth: .infinity, alignment: .leading)` on the left VStack and no explicit alignment on the right Text. In SwiftUI, the right Text will naturally align to the trailing edge of the HStack. This is the correct way to achieve right-aligned metrics. However — see Note 2 below.

## Part B: Device Verification Checklist

### Routing Insights (ContentView — `routingInsightsSection`)

- [ ] **Crowding with real data:** The row layout is:
  - Left: `VStack` (model name + route label), `.frame(maxWidth: .infinity, alignment: .leading)`
  - Right: metrics text, natural trailing alignment

  With the card at `padding: 10` and row at `spacing: 0`, the left column will fill available space and the right text will anchor to the trailing edge. The truncation mode on the route label is `.middle` which is appropriate for long model strings. **Test with real data:** if `currentRouteLabel` exceeds ~30 characters, does the row wrap or the metrics get squished?

- [ ] **Lopsided feel:** The three rows (Opus/Sonnet/Haiku) are always rendered — there is no empty state for the whole section. If all three rows have no metrics, the right column will show three dim dashes. Verify this does not look like an unpopulated table. The `inkFaint` color should make it clear these are absent values, not errors.

- [ ] **Relationship to Runtime activity card above:** There is no explicit visual grouping between `kpiSection` (with `MBKpi` cells) and `routingInsightsSection`. Both are separated by `.padding(.top, 10)`. Verify the KPI values and the routing insights rows read as two distinct information panels. The section header "Routing insights" should make the boundary clear; check whether the 10pt gap plus the card backgrounds provides enough separation from the KPI card above.

### Upstream Tab — Spacing Sequence

- [ ] **Token status vertical weight:** This section has 4 MBField rows (Access token, Last refresh, State, Refresh) + a conditional error. The section above it (Subscription auth) also has 3-4 MBField rows + conditional next-step. Two adjacent information-dense sections may feel top-heavy and push the save/reload button row too far down the scroll. **Verify:** after filling in routing rules, does the save button appear within the first scrollable viewport, or does the user need to scroll to see it?

- [ ] **Routing rules Add button:** The `Add rule` button sits directly beneath the `List` card with only the default 8pt MBSection gap. The `List` card has `maxHeight: 260`. When the list is near empty (0-1 rules), the Add button may appear visually disconnected from its associated list. Check whether adding a small `Spacer(minLength: 4)` or `padding(.top, 4)` between the List and the button improves the grouping perception.

- [ ] **Fallback route / Advisor route sections:** Both use `RouteDraftPickers` with three pickers in an HStack. On narrow settings window widths, these may compress awkwardly. Verify the pickers do not overflow the 760pt max-width settings shell.

### Consistency Under Dynamic Conditions

- [ ] **Token status polling:** The `.task { await model.startTokenStatusPolling() }` on `UpstreamSettingsTab` polls every 30 seconds. The MBField values update in-place. Verify that rapid MBField updates do not cause layout shifts or flicker. This is especially relevant for the "Last refresh" text which will change from "just now" to "31 seconds ago" etc.

- [ ] **Dark mode:** All colors are via `MBColor.dynamic` or fixed system colors. No hardcoded hex values used in the new sections. Verify the `routingSaveError` and `tokenRefreshError` text is legible in dark mode (they use `MBColor.faultInk` which is `rgb(0x823228)` in light and `rgb(0xE4A297)` in dark — both legible).
