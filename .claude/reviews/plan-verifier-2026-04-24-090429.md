## [AR] Architecture Review

### Entry points touched
- `AnthropicBridge.updateRouting(table:, advisorRoute:)` — new actor method. Entry from `GatewayDaemon.applyRoutingUpdate`. No conflict with existing public surface.
- `GatewayDaemon.applyRoutingUpdate(table:, advisorRoute:)` — new. Entry from `AppModel.saveRoutingAndApply`.
- `ResolvedRoute` type — new, in `ModelRouting.swift`. Not serialized (verified: `RouterConfigurationStore.swift` only encodes `ModelRoutingTable` / `ModelRoute`, never `PreparedTurn` or `PendingToolTurn`). Safe transient type.

### Hot-reload invariant
**Plan claim:** in-flight requests continue with old route because each task closure captures `resolvedRoute` at `prepareTurn` time.
**Verified:** `prepareTurn` at `AnthropicBridge.swift:517` computes `resolvedRoute` and stores it on `PreparedTurn` (line 545) which is then passed into `runPreparedTurn`. Once `runPreparedTurn` is entered, the bridge's private `routingTable` is no longer read during that request — the `resolvedRoute` is carried on the local `preparedTurn: PreparedTurn` argument. Concurrent `updateRouting` changing `self.routingTable` is therefore invisible to the in-flight request. Claim holds.

**Caveat:** Task 5 step 1 moves `configuration.routingTable` into a separate bridge-local `var routingTable`. The bridge's `configuration: RouterConfiguration` stays `let`. But `configuration.routingTable` computed accessor no longer aligns with the live bridge state — any future code that reads `configuration.routingTable` (vs `self.routingTable`) will see stale data. Plan step 2 requires "grep 确认" 4 sites; this is correct but the plan should state explicitly: "after this refactor, `self.configuration.routingTable` / `self.configuration.advisorRoute` must never be read; only `self.routingTable` / `self.advisorRoute`". That could be enforced via a comment at the declaration or, better, a private helper. Advisory.

### Replacement completeness
Plan lists `configuration.routingTable` / `.advisorRoute` replacement sites: `:391 :442 :517 :1074` — verified by grep. Complete.

### Persistence layer impact
`RouterConfigurationStore` encodes `RouterConfiguration`; `ResolvedRoute` never leaves the bridge boundary. On-disk schema unchanged. ✅

Summary: 1 advisory architectural concern (accessor ambiguity after split), no must-revise items.

### Pre-check: Threat Model presence

### Input injection (routing editor)

### Input injection (upstream model / effort / verbosity fields)

But plan note at end of step 3 says "其他从 UI 选出时若上游拒绝会在请求时失败并 trace，本 Phase 不拦截" — if the whitelist diverges from upstream acceptance, the user sees failure at request time, not at save time. Acceptable trade-off (the whitelist is Phase 2 probe-derived), but plan should note where the whitelist source of truth is (`docs/scheme3/10-tool-mapping-v1.md §7.8`).

### Resource lifecycle (polling Task in Task 10)
Plan Task 10 step 1: `func startTokenStatusPolling()` / `stopTokenStatusPolling()` uses `Task` + sleep loop + `.task(id:)` lifecycle. Cleanup triggers:
- on-success: not applicable (infinite loop)
- on-error: `try? await Task.sleep` swallows cancellation. On cancellation, loop body exits at next sleep.
- on-view-disappear: `.task` auto-cancels — **but** only if the `.task` modifier is correctly placed on `UpstreamSettingsTab.body` (see Assertion 5). If the plan's `.task(id: SettingsTab.upstream)` on AppModel doesn't compile, the lifecycle binding is broken and the polling may leak across app lifetime.
- on-app-termination: SwiftUI cleans up on app quit. Acceptable.

**Gap (cross-ref Assertion 5):** polling Task cancellation depends on `.task` placement semantics; plan's placement is underspecified and visibility-broken.

### Failure visibility
Plan Task 10 covers `refreshTokenNow()` error surfacing via `tokenRefreshError`. Task 5 logs `routing_hot_reload` stage on update. `saveRoutingAndApply` "失败时 publish `routingSaveError`" — see S2 runtime regression #2: plan doesn't distinguish persist-failed vs apply-failed. Minor advisory.

### Token preview (DoctorSnapshot)
Plan Task 9: `accessToken.prefix(4) + "…" + accessToken.suffix(4)`. This exposes 8 characters + separator. Consistent with existing `access_token_suffix` emission at `AnthropicBridge.swift:129` (already ships 4 chars). Plan threat model acknowledges.
