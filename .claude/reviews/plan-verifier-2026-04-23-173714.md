**[断言 1] Task 5: `handleMessages` 外层 do-catch 捕获不到 upstream 401，因为 `responsesClient.streamEvents` 只在 body-producing 闭包内被调用（`runPreparedTurn:441`），而该闭包在 `return HTTPResponse(statusCode: 200, ..., stream:{...})` 返回后、headers 已 flush 时才执行。**

验证：
- `AnthropicBridge.swift:82-95` — `handleMessages` 在 prepareTurn 成功后立刻 `return HTTPResponse(statusCode: 200, ...)`，把 `runPreparedTurn` 包在 `stream:` 闭包里
- `AnthropicBridge.swift:441` — `let stream = try await responsesClient.streamEvents(...)` 仅在 `runPreparedTurn` 内被调用
- `LocalHTTPServer.swift:402-414` — `connection.send(content: headerBytes, ...)` 先执行（含 `statusCode: 200`），然后才 `try await producer(writer)` 调用我们的闭包
- `ResponsesClient.swift:47-53` — 401 来自 `streamEvents` 的 `guard (200..<300).contains(httpResponse.statusCode) else { throw ResponsesHTTPError(...) }`，这是 access_token 过期时 upstream 首个响应状态码的触发点，永远在 `runPreparedTurn` 内部抛出
- `AnthropicBridge.swift:97-111` — 外层 catch `ResponsesHTTPError` 只能捕获 `prepareTurn` 同步抛出的错误；`prepareTurn` (line 173-424) 不调用 `responsesClient.*`

结果：❌ 断言成立 [C:95] → **Must-revise**：计划 Task 5 的核心前提错误。expired access_token 的 401 永远发生在流闭包内部，headers 已 200 OK flush 出去，无法通过 `return anthropicError(503)` 响应。Task 5 Step 2 "流中 401 通常不会发生" 与计划 Goal "access_token 过期时 daemon 自动刷新" 直接矛盾 — 过期场景正是下次请求 `streamEvents` 首次握手就 401 的场景。

具体修订建议：
- **方案 A（推荐）**：在 `handleMessages` 内（`prepareTurn` 之后、`return HTTPResponse(stream:...)` 之前）显式做一次 `let stream = try await responsesClient.streamEvents(payload, credentials:)`，捕获 401 → `refreshAndReload` → 重新 `streamEvents`。成功后把拿到的 `stream` 传给 `runPreparedTurn`（需要重构 `runPreparedTurn` 接收已建流而非再自己建流）。这样 headers 尚未 flush，401 可以映射为 503。
- **方案 B**：在闭包内把 401 转成 SSE `event: error` 帧 + `finish(stopReasonHint:)` 再 throw（`LocalHTTPServer.swift:420-423` 已有 `committedStreamFailure` 语义）。但此时 client 已收到 200 + Content-Type: text/event-stream，不符合 Anthropic 503 约定；只能作为 fallback。
- **方案 C**：弃用流式返回，改走 buffered response（违反现有 Phase 4 架构，不推荐）。

无论选哪个方案，**Task 5 Step 1 的流程描述（"try await streamEvents ... 若抛 401"）必须重写以反映真实代码路径**，且 Step 2 的 "流中 401 不在 scope" 判断必须撤回 — 这就是 scope 本身。

此外 `runPreparedTurn` 内另有 2 处 `streamEvents` / `perform` 调用（`AnthropicBridge.swift:791` second-pass、`:947` advisor），它们不在 Phase 5 scope 内说得通（二次请求发生在同一会话的第二轮，access_token 刚用过，瞬时过期概率极低），但应在修订后的计划中**显式声明**这两处不处理，避免隐性假设。

**[断言 2] Task 4 Step 3 的原子写实现描述与 DP-P5-003 选定方案矛盾：前者写 `Data.write(to: authFileURL, options: [.atomic])`，后者选定 `FileManager.replaceItemAt`。两者语义不同，前者无法满足 DP-P5-003 的"保留 0600 权限"目标。**

验证：
- 计划 line 224-225：`let data = try JSONEncoder().encode(payload); Data.write(to: authFileURL, options: [.atomic])`
- 计划 line 456-460 (DP-P5-003 Chosen)：`C — 使用 FileManager.default.replaceItemAt 自动保留原文件属性；比 A 少一次 syscall，比 B 少 race condition`
- 计划 Threat Model line 55：`FileManager.default.replaceItemAt 或 Data.write(to:options:.atomic) 内部管理 temp file` — 把两个 API 混为一谈

事实：`Data.write(..., .atomic)` 写临时文件 + rename，**不保留** destination 的 posixPermissions（创建的临时文件以默认 umask 0644 为典型结果，rename 后原 0600 丢失）。`FileManager.replaceItemAt` 确实保留 destination attributes（macOS APFS 语义）。这两个 API 不能互换。

结果：❌ 断言成立 [C:95] → **Must-revise**：Task 4 Step 3 必须用 `FileManager.default.replaceItemAt(authFileURL, withItemAt: tempURL, backupItemName: nil, options: [], resultingItemURL: nil)`；临时文件位置用 `FileManager.default.url(for: .itemReplacementDirectory, in: .userDomainMask, appropriateFor: authFileURL, create: true)` 获取。同步修正 Threat Model 表格第 1 行（Task 4），让 cleanup 描述只提 `replaceItemAt`。
